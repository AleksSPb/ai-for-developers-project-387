# Соглашение об именовании веток

Проект следует Conventional Commits, но в урезанном виде: не одиннадцать
типов коммитов, а три — столько же, сколько нужно для повседневной работы
над приложением.

## Формат

```
<префикс>/<описание>
```

Описание — латиницей в `kebab-case`, глаголом первым. Одного слова
достаточно, длиннее трёх-четырёх смысла нет.

| Ветка | Когда |
|---|---|
| `feat/add-call-form` | новая пользовательская функция |
| `fix/double-submit` | баг |
| `docs/api-readme` | документация |

## Префиксы

| Префикс | Когда |
|---|---|
| `feat` | новая пользовательская функция |
| `fix` | исправление бага |
| `docs` | README и документация |

Префикс совпадает с типом коммита из
[соглашения о сообщениях коммитов](conventional-commits.md) — ветка и её
коммит читаются одинаково.

## Правила

1. Только три префикса из таблицы выше. Других нет: ветка, которую нельзя
   назвать одним из них, скорее всего не нужна.
2. Описание — латиницей, `kebab-case`, без дат, номеров задач и `v2`.
   Номер задачи живёт в футере коммита (`Refs: #14`), версия — в
   `vite-project/package.json` и в тегах release-please.
3. Одна ветка — одна задача. Работа ведётся от свежего `main`, `main`
   не форкачится.
4. Служебные ветки не переименовываются. Их создаёт и удаляет release-please,
   на них завязан релизный workflow. Ветка одна и без компонента в имени:
   `release-please--branches--main`. Пакетов два, а `separate-pull-requests` не
   задан, поэтому Merge-плагин сливает всех кандидатов — включая snapshot —
   в один PR и подставляет имя ветки жёстко, без компонента.

## Существующие ветки

В репозитории только `main` и служебная ветка release-please — истории
именования, к которой пришлось бы подстраиваться, нет.
